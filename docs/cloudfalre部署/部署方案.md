# PersonalSite-home 静态部署 + GitHub 驱动的内容管理方案

> 目录说明：本目录名 `cloudfalre部署` 为原始指定名（cloudflare 拼写少一个 r），建议后续重命名为 `cloudflare部署`，本文统一按正确拼写 **Cloudflare** 表述。

## 1. 目标与边界

- **硬约束（用户指定，不可改动）**：本项目走 Cloudflare 静态部署。
- **核心诉求**：首页内容与布局参考 `PersonalSite` 项目；后续新增 `/admin` 页面用于修改内容，修改动作落地到 **GitHub 仓库文件**，由 Cloudflare 自动重新构建发布。
- **隐含诉求**：前端页面托管在 Cloudflare，流量近乎无限、免自建后端服务器。

## 2. 现状梳理

| 维度 | 参考项目 `PersonalSite` | 当前 `PersonalSite-home` |
|------|------------------------|--------------------------|
| 首页数据来源 | `getSiteConfig()` 服务端动态读取 | `import profile from "@/data/profile"` **构建期静态导入** |
| 部署方式 | Next.js standalone (SSR) + `BUILD_STATIC=1` 可转 export | `opennextjs-cloudflare`（Workers，`build:worker`） |
| Admin | `/admin` → `/api/admin/config`（服务端写文件，实时生效） | 无 |
| 数据落地 | 服务端文件系统 | 仓库内 `src/data/*.ts` |

**关键结论**：`PersonalSite-home` 的首页数据已经是**构建期静态导入**（不是 SSR 动态读取），这天然适配「改文件 → 重新构建」。也就是说，不需要像参考项目那样依赖服务端写文件，直接把数据文件写回 GitHub 即可触发重建，方案比参考项目更简洁。

## 3. 方案架构（数据流）

```
[浏览器] /admin 页面
   │  (用户输入，Bearer Token 鉴权)
   ▼
[GitHub REST API] PUT /repos/{owner}/{repo}/contents/src/data/profile.ts
   │  (提交 src/data/profile.ts / homepage.ts 的改动)
   ▼
[GitHub push] ──webhook/集成──▶ [Cloudflare Pages 自动构建]
   │
   ▼
[opennextjs-cloudflare build] → 重新打包静态资源 → 发布
   │
   ▼
[首页刷新] 读取新的 profile.ts → 内容更新（构建后生效，约 1–3 分钟）
```

一句话：**admin 是纯前端页面，改的是仓库里的数据文件，不是数据库**。Cloudflare 只负责托管构建产物，因此流量无限、无后端成本。

## 4. 可行性结论

**结论：方案可行，且比参考项目更轻。** 但需注意以下权衡：

### 优势
1. **流量无限 + 零后端**：Cloudflare Pages 免费配额对静态流量极宽松，不用租服务器、不用运维。
2. **数据即代码**：所有内容都在 Git 历史里，可回滚、可审计、可多人协作。
3. **与现状契合**：home 已是构建期导入数据，无需引入 SSR 写文件链路。
4. **与 opennextjs-cloudflare 兼容**：admin 是纯客户端组件，构建链路（`build:worker`）不变。

### 风险与限制（必须知晓）
1. **「实时」降级为「准实时」**：每次保存 = 一次 push = 一次构建。Cloudflare Pages 免费版**每日构建上限 500 次**，频繁保存可能撞上限；且生效有 1–3 分钟延迟（参考项目的 SSR 是秒级实时）。
2. **凭据暴露在浏览器**：前端直连 GitHub API 必须把 Token 放在浏览器（参考项目也是 localStorage 存 Token）。必须用 **fine-grained PAT**，仅授权该仓库的 `contents:write`，并支持随时吊销；不要使用全权限 Token。
3. **本地冲突**：admin 写的是仓库文件，你本地 `git pull` 才能在本地同步；否则下次本地提交会冲突。建议 admin 改动后用 `git pull --rebase`。
4. **分支策略**：建议 admin 写入一个固定分支（如 `main` 或 `content`），由该分支触发 Pages 生产构建；避免直接污染你正在开发的代码分支。
5. **内容校验**：admin 提交前应在浏览器端做基础校验（必填、URL 合法性），避免提交脏数据导致构建失败。

## 5. 落地步骤（分阶段）

### 阶段 A：内容数据外置（已完成基础）
- 当前 `src/data/profile.ts` 与 `src/data/homepage.ts` 已是数据源，首页已引用。
- 若要把首页布局/效果对齐参考项目，把 `PersonalSite/src/components/home/*`、`src/components/sections/*`、`src/components/reactbits/*` 等搬入 home，并让它们消费 `profile`/`homepage`。

### 阶段 B：新增 `/admin` 页面（前端 + GitHub 写回）
- 复用参考项目的 `src/app/admin/page.tsx` 表单结构（tab 分组、字段映射）。
- 移除对 `/api/admin/config` 的依赖，改为调用 GitHub API：
  - `GET` 当前文件内容：`GET /repos/{owner}/{repo}/contents/src/data/profile.ts` 取 `sha` 与 base64 内容。
  - `PUT` 写入：`PUT /repos/{owner}/{repo}/contents/src/data/profile.ts`，body 含 `message`、`content`（UTF-8→base64）、`sha`。
  - 鉴权：`Authorization: Bearer <PAT>`，Token 存 `localStorage`（与参考项目一致）。
- 表单字段与 `profile.ts` / `homepage.ts` 的字段对齐（`name`、`role`、`tagline`、`social`、`contents`、`mbti` 等）。

### 阶段 C：Cloudflare Pages 接入 GitHub
- 在 Cloudflare Pages 后台「连接 Git 仓库」，选择本仓库，构建命令 `pnpm build:worker`（即 `opennextjs/cloudflare build`），输出目录 `.open-next/assets`。
- 启用「每次 push 自动部署」。建议单独分支或 `production` 分支触发。
- Token 仅在前端使用，无需写入 Cloudflare 环境变量；但若想进一步收紧，可加一个 Worker 代理持有 Token（会引入轻量后端，与「纯前端」诉求略有偏离，按需取舍）。

### 阶段 D：校验与安全
- 在 GitHub 创建 fine-grained PAT，`Repository permissions → Contents: Read and write`，只对这一个仓库。
- 文档化「admin 使用须知」（Token 来源、保存即发布、需 pull 同步）。

## 6. 关键实现片段（GitHub 写入示例）

```ts
// admin 端：读取现有文件 sha（写回必须带 sha，否则 409）
async function fetchFile(path: string, token: string) {
  const res = await fetch(
    `https://api.github.com/repos/${OWNER}/${REPO}/contents/${path}`,
    { headers: { Authorization: `Bearer ${token}`, Accept: "application/vnd.github+json" } }
  );
  const data = await res.json();
  return { sha: data.sha, content: data.content };
}

async function saveFile(path: string, token: string, content: string, sha: string) {
  await fetch(`https://api.github.com/repos/${OWN, }/${REPO}/contents/${path}`, {
    method: "PUT",
    headers: { Authorization: `Bearer ${token}`, "Content-Type": "application/json" },
    body: JSON.stringify({
      message: "chore: update site content via admin",
      content: btoa(unescape(encodeURIComponent(content))),
      sha,
    }),
  });
}
```

## 7. 与「参考项目 SSR 方案」的取舍

| 维度 | 参考项目（SSR 写文件） | 本方案（GitHub 驱动） |
|------|------------------------|------------------------|
| 生效速度 | 秒级实时 | 重建后 ~1–3 分钟 |
| 后端 | 需要 Node 运行时写文件 | 无后端，纯静态 |
| 流量成本 | 取决于服务器 | Cloudflare 近乎无限 |
| 数据持久 | 服务器磁盘 | Git 仓库（可回滚） |
| 复杂度 | 服务端 API | 前端直连 GitHub API |
