# 静态资源 vs 动态请求分析（部署到 Cloudflare Workers）

> 结论先行：本项目部署到 Cloudflare Workers 后，**并非「除后台更新外全是静态资源」**——还有 `/admin` 页面本身及登录/登出接口会触发 Worker 调用。但浏览型流量（访客看首页、看图）确实全是静态资源，不消耗 Worker 算力。

## 1. 实际路由清单（已核实项目源码）

| 请求 | 类型 | 是否 Worker 调用 | 说明 |
|------|------|----------------|------|
| `/`、`/about`、首页各区块 | 静态资源 | ❌ 不调用 | 构建期预渲染，走 Static Assets 边沿直出 |
| 图片（`/mbti/*.png`、`/images/*`）、JS / CSS / 字体 / SVG | 静态资源 | ❌ 不调用 | 同上，均为构建产物 |
| `/admin` 页面本身 | **动态** | ✅ 调用 Worker | 登录网关设了 `force-dynamic`，每次打开服务端校验 Cookie |
| `/api/admin/login` | 动态 | ✅ 调用 Worker | 校验口令、下发 HttpOnly Cookie |
| `/api/admin/logout` | 动态 | ✅ 调用 Worker | 清除 Cookie |
| `/api/admin/update` | 动态 | ✅ 调用 Worker | 写回 GitHub 文件（即「后台更新」） |

- 动态标识来源：`src/app/admin/page.tsx` 与三个 `route.ts` 均含 `export const dynamic = "force-dynamic"`。
- 其余页面默认静态，`npm run build` 显示 `○ Static`，已预渲染进 `.open-next/assets`。

## 2. 部署结构（`wrangler.jsonc` 已确认）

```
main:     .open-next/worker.js        # Worker 入口（仅处理动态部分）
assets:   .open-next/assets (ASSETS)  # 静态资源绑定，边沿直出、不走 Worker 算力计费
```

请求到达时：若路径命中 `assets` 中的静态文件 → Cloudflare 边沿直接返回，不调用 Worker；
若未命中（动态页面 / API）→ 交由 `worker.js` 处理。

## 3. 「静态资源不费流量」的前提修正（重要）

这是做成本判断时最容易混的点：

- **Worker 算力 / 请求数计费**：静态资源走 Cloudflare **Static Assets** 绑定，命中即在边沿返回，**不触发 Worker 调用**，因此不花 Worker 的请求数 / CPU 费用。✅ 这部分理解正确。
- **带宽（egress）流量**：静态资源**仍然产生出网带宽**，而带宽正是 Cloudflare 会计量的部分。因此「流量无限」并不准确——Cloudflare 有免费额度（请求数 + 带宽上限），超出后按量计费，只是额度大、单价低，并非字面意义的无限。

**一句话：静态资源省的是「Worker 算力」，不是「网络流量」。**

## 4. 对本项目的实际成本影响

- **访客侧**：几乎全是 Static Assets，Worker 调用接近 0 → 「纯前端页面」设计目标达成，主要成本是带宽而非 Worker 调用。
- **后台侧**：`/admin` + 3 个 `/api/*` 是仅有的 Worker 调用，且 admin 是低频操作（单人使用），Worker 成本可忽略。
- **首页等页面**：虽是静态 HTML，但已预渲染进 `assets`（`○ Static`），确认走静态而非 SSR，不会误触发 Worker。

## 5. 可选进一步优化

可将 `/admin` 登录网关从「服务端 `force-dynamic`」改为「纯静态页面 + 仅在登录接口校验」：

- 优点：`/admin` 页面本身也变静态资源，仅登录那一刻打 Worker。
- 代价：未登录者能在前端看到表单壳（但提交会被 401 拦截）。

当前「服务端网关」方案更安全，**建议保留**——admin 访问频率低，这点 Worker 调用无关紧要。
