# 后台可配置化方案设计（PersonalSite / 清正）

> 设计时间：2026-08-27
> 项目：Next.js 16（App Router）静态展示站，当前配置全部硬编码于 TS 文件
> 目标：把「页面文案 / 社交链接 / MBTI / SEO」等配置，从「改代码重新构建」变为「后台可视化编辑」

---

> **🟢 已落地状态（2026-08-28）**：最终采用 **Node SSR + Docker + 文件写穿透** 方案（即下文 §12.4），已在本分支实现完毕，构建与本地 standalone 冒烟测试通过。原 §2 推荐的 Keystatic（方案 A）已被此方案取代——因为需求明确要求「后台改完实时生效 + 单用户 + 不备案 + 国内流畅」，文件写穿透比 Git-backed CMS 更直接。详见文末 §14。

## 0. 现状盘点（要后台化的配置清单）

| 配置项 | 当前位置 | 当前形态 | 是否需要后台 |
| --- | --- | --- | --- |
| 姓名 / 角色 / 标语 / 所在地 / 邮箱 / 简介 | `src/data/profile.ts` | 编译时常量 | ✅ 是 |
| 社交 URL（微信 / 小红书 / 微博） | `profile.social` | 编译时需改 TS | ✅ 是 |
| MBTI 全部数据（类型/维度/优缺点） | `profile.mbti` | 编译时常量 | ✅ 是 |

**痛点**：当前改任何文案都要改 TS 文件 + 重新构建，且需要会代码的人操作。运营（如 xianyu）无法自助。

---

## 1. 需求拆解

- **操作者**：非技术的运营/本人，希望像填表单一样改文案
- **频率**：低频（月度级），不需要秒级实时生效
- **实时性**：接受「改完 → 重新构建后生效（分钟级）」，不要求即时
- **部署约束**：此前已定「不备案 + 中国香港/海外静态托管 + 国内流畅」，方案不能破坏这个前提

---

## 2. 四类方案对比

| 方案 | 原理 | 实时性 | 是否需要后端运行时 | 是否破坏「静态/免备案」 | 适合度 |
| --- | --- | --- | * | --- | --- |
| **A. Git-backed CMS（Keystatic / Decap）** | 内容存 Git 仓库，Web 编辑器通过 GitHub OAuth 登录，改动 commit 回仓库并触发重新构建 | 分钟级（构建后） | ❌ 不需要 | ✅ 兼容，仍是静态导出 | ⭐⭐⭐⭐⭐ 推荐 |
| **B. Headless CMS（Payload / Sanity / Strapi）** | 独立 CMS 后台 + 数据库，前端运行时拉取 | 实时 | ✅ 需要 Node/DB 服务 | ❌ 需服务端，部署形态大改 | ⭐⭐⭐ |
| **C. 自建 Admin + SQLite/PG** | 自己写 `/admin` 页面 + Route Handlers + 数据库 | 实时 | ✅ 需要 Node 运行时 | ❌ 放弃静态导出 | ⭐⭐ |
| **D. 构建时拉取远程 JSON** | 构建脚本从私有 JSON/Gist 拉取写入 profile | 构建后 | ❌ 不需要 | ✅ 兼容 | ⭐⭐⭐ |

**结论**（结合本项目约束）：方案 A（Git-backed CMS）最契合——零后端、免费、非技术可用，且与「香港静态托管 / 免备案」完全兼容。方案 B/C 需要服务端运行时，会颠覆当前静态架构，除非后续需要「改完即时生效」才值得。

## 3. 推荐方案：Git-backed CMS（以 Keystatic 为例）

### 3.1 数据流

```
运营/本人 ──登录(GitHub OAuth)──> Keystatic Web 编辑器
        │  (填写表单：姓名/标语/社交/MBTI…)
        ▼
   改动写入 ──> 仓库内容文件 (content/*.json 或 .yaml)
        │  (Git commit)
        ▼
   CI / 构建 (pnpm build) ──> 构建脚本读取内容文件 ──> 生成 profile/homepage 数据
        │
        ▼
   站点重新发布 (Cloudflare Pages / EdgeOne / 香港静态托管)
```

### 3.2 为什么契合本项目

- **不改部署形态**：仍走静态导出（`output: "export"` → `out/`）或当前 Worker 路线，与中国香港静态托管无缝衔接，免备案不受影响。
- **非技术可用**：Keystatic 提供表单化 Web 编辑器，运营无需懂代码。
- **零成本**：用 GitHub 仓库 + OAuth，无数据库、无月度账单。
- **可审计**：每次改动都是 Git commit，有历史、可回滚。

### 3.3 与本项目的接入点

- 用 Keystatic 的 `keystatic.config.ts` 定义字段（name / role / tagline / social / mbti / philosophy / focus / seo）。
- 内容放在 `content/site.json`（取代 `profile.ts` / `homepage.ts` 的常量）。
- 构建脚本（或 `keystatic` 的 Next.js 集成）在构建时把内容注入页面——即把「写死的 TS 常量」替换为「读取内容文件」。
- 社交图标 BRAND 映射保留硬编码，仅 URL 走内容文件。

##  ｜4. 备选方案：自建 Admin + SQLite（实时生效）

若后续需要「改完立即生效、不重新构建」，走此路线：

- 增加 `src/app/api/config` Route Handlers + SQLite（或 PostgreSQL）；
- 增加 `/admin` 登录页（简单口令或 OAuth）；
- 前端改为运行时读取（放弃 `output: "export"），改用 Node SSR / Edge 运行时；
- 部署需服务端（Cloudflare Workers + D1，或 EdgeOne/Paas 的 Node）。

代价：架构复杂度显著增加，且静态/免备案前提会被打破（需服务端节点）。**当前不推荐**，仅作「未来若需实时」的备选。

## 5. 落地步骤（推荐方案 A）

1. 在仓库新建 `keystatic.config.ts`，声明所有可配置字段（对齐上面的清单）。
2. 把 `profile.ts` / `homepage.ts` 的常量迁移为「从 Keystatic 内容读取」——保留类型校验。
3. 接入 Keystatic 的 Next.js 组件（或独立编辑器路由），配置 GitHub OAuth（运营需 GitHub 账号）。
4. 在 CI（Cloudflare Pages / EdgeOne / GitHub Actions）中确保「内容改动 → 自动构建」。
5. 本地 `pnpm build` 验证：改内容文件 → 构建 → 页面生效。

## 6. 风险与建议

- **OAuth 门槛**：Git-backed CMS 需要运营有 GitHub 账号并授权；若运营无 GitHub，可改用方案 D（远程 JSON + 简易口令上传）作为降级。
- **构建频率**：每次修改都触发一次构建，频率低无影响；若改得勤，注意平台构建额度。
- **图片资源**：头像 / OG 图若也要后台换，Keystatic 支持文件字段（存仓库或对象存储）。
- **与既有静态导出兼容**：`next.config.ts` 当前是 Worker 路线（非 export），Keystatic 内容在构建时注入同样适用，无需强制 `output:"export"`。

## 7. 远程 JSON 存储选型（方案 D 细化）

「远程 JSON」指构建时（或前端运行时）从一个 URL 拉取配置。存储位置要在「运营能顺畅上传（国内）」与「构建机能顺畅拉取」之间取舍：

| 存储 | 国内上传（运营） | 海外 CI 拉取 | 国内前端读取 | 备注 |
| --- | --- | --- | --- | --- |
| **腾讯云 COS / 阿里云 OSS（中国香港）** | ⭐⭐⭐⭐ 快 | ⭐⭐⭐ 可行 | ⭐⭐⭐⭐ 快 | 香港免备案、对大陆延迟低，两端兼顾，**推荐** |
| Cloudflare R2 | ⭐⭐（需 API/CLI） | ⭐⭐⭐⭐ 快 | ⭐⭐ 不稳定 | 海外 CI 友好，国内上传/读取不稳 |
| GitHub 私有仓库（文件即 JSON） | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | 本质等同方案 A，不如直接用 Keystatic |
| 阿里云 / 腾讯云 OSS（大陆） | ⭐⭐⭐⭐⭐ 最快 | ⭐ 需备案/跨海 | ⭐⭐⭐⭐⭐ 最快 | 国内最快，但 CI 海外拉取慢、且需备案 |

**推荐**：方案 D 若落地，JSON 放 **中国香港地域对象存储（腾讯云 COS / 阿里云 OSS）**——
- 运营在国内上传快，香港节点对大陆延迟低；
- 构建机（即使海外）走公网也能拉取；
- 用「私有桶 + 临时签名 URL」或「带 Token 的上传接口」保护写入，避免任何人篡改站点配置。

**两种拉取模式的区别（决定「中国友好」侧重哪一端）：**
- **构建时拉取**（CI 构建机读取）：读取端在海外，优先保证「海外可读」→ 香港/OSS 均可；拉完编译进静态页，前端无需联网。
- **前端运行时拉取**（浏览器读取）：读取端是国内访客，优先保证「国内可读」→ 必须挂国内/香港 CDN，且每次访问多一次请求。

> 若希望运营「点点就能上传」而非用 CLI/API，纯裸 JSON 体验不佳；此时方案 A（Keystatic）自带可视化编辑器更合适。

## 8. 综合方案：不备案 + 国内流畅 + 后台可控（实时 / 按钮部署）

> 完整约束：① 不备案（不能指向大陆服务器）② 国内流畅访问 ③ 后台可改配置 ④ 改完**实时生效**，或后台「点按钮重新部署」均可接受。

### 8.1 候选方案对比

| 方案 | 实时性 | 国内访问 | 是否需服务器 | 与现有架构关系 | 适合度 |
| --- | --- | --- | --- | --- | --- |
| **A. Cloudflare Workers + KV + 轻量 Admin** | 实时（读 KV） | 中等（海外 CDN，略慢于香港） | ❌ 无服务器 | ✅ 复用已配好的 Worker 路线 | ⭐⭐⭐⭐ 复用优先 |
| **B. 中国香港 Node 服务 + SQLite/PG + Admin** | 实时（读 DB） | ⭐⭐⭐⭐ 最快最稳 | ✅ 需香港 ECS/容器 | 放弃静态导出，改 Node SSR | ⭐⭐⭐⭐ 国内最优 |
| **C. 中国香港静态 + 后台「点按钮重新部署」** | 分钟级（触发构建） | ⭐⭐⭐⭐ 快 | ❌ 无需服务器 | ✅ 复用静态托管 | ⭐⭐⭐⭐ 省心 |

### 8.2 推荐

- **首选 A（Cloudflare Workers + KV）**：本项目已配好 OpenNext → Workers，直接加一个 KV 命名空间存配置、一个受密码/Token 保护的 `/admin` 页面写 KV、前端运行时读 KV。改动最小、免服务器、免备案、实时生效。代价：Cloudflare 国内访问不如香港节点稳。
- **国内访问最优选 B**：若「国内流畅」权重最高，用中国香港 Node（腾讯云/阿里云香港）+ SQLite，放弃静态导出，Admin 改 DB 实时生效；代价是要维护一台服务器。
- **最省心选 C**：若不想放弃静态架构，后台「改 JSON → 触发 CI 重新部署到香港静态托管」，分钟级生效。

### 8.3 架构（以 A 为例）

```
运营 ──登录(口令/Token)──> /admin 页面 ──写──> Cloudflare KV(配置)
                                        │
访客浏览器 ──> Worker 站点 ──运行时读 KV──> 渲染页面（实时生效）
```

### 8.4 实施要点

- KV / DB 写入必须有鉴权（Token 或口令），避免公开篡改站点配置。
- `profile.ts` 改为「KV / DB 读取 + 本地默认值兜底」，构建时不再写死常量。
- 若选 B，需把 `next.config.ts` 从 Worker/export 改为标准 Node 部署（EdgeOne / 香港 PaaS）。
- 若选 C，「点按钮重新部署」即后台调用 CI API（Cloudflare Pages / EdgeOne Builds / GitHub Actions）触发一次构建。

## 9. 备案与 DNS 澄清（重要）

> 常见误解：「不备案就只能使用 Cloudflare 解析」。这是错的。

- **备案触发条件**：ICP 备案只看「域名最终指向的服务器是否在中国大陆境内」。指向大陆服务器 → 必须备案；指向中国香港 / 海外 → **免备案**。
- **DNS 解析服务商与备案无关**：阿里云 DNS、DNSPod、Cloudflare、Namesilo、Godaddy 等都能把域名指向香港 / 海外服务器，都**不需要备案**。
- **Cloudflare 不是必须**：只有需要它「代理 / CDN（橙色云）」隐藏源站或加速时才用；纯解析（灰色云）与普通 DNS 无区别。
- **域名实名**：`.cn` 注册需实名（与备案是两回事）；`.com` / `.top` 等经境外注册商可不实名。
- **结论**：「不备案 + 国内流畅」= 域名解析到**中国香港 / 海外节点**（香港服务器、Cloudflare Workers、Vercel 等），用任意 DNS 即可；要隐藏源站 / 加速再开 Cloudflare 代理。

## 10. 静态部署与后台生效：矛盾与现成 Docker 产品

> 关键认知：纯静态站点（无运行时）无法「运行时实时」读取后台数据。后台改完即时生效，必须有运行时（服务器 / 容器 / 边缘函数）。

### 10.1 两条路线

- **静态 + 重新构建（免服务器、免费）**：Decap CMS（原 Netlify CMS）/ Keystatic。后台改内容 → commit 回 Git → 触发 CI 重新构建。分钟级生效，无需后端，适合低频改文案。
- **放弃纯静态、上运行时（需容器 / 服务器）**：后台实时生效，必须有运行时支撑。

### 10.2 现成 Docker / 开源产品（软件免费、可 docker-compose 一键起）

| 产品 | 类型 | 软件授权 | 说明 |
| --- | --- | --- | --- |
| Directus | Headless CMS | ✅ 开源免费 | docker-compose 一键起，自带后台 UI + 数据库，前端拉 API |
| Payload | Headless CMS | ✅ 开源免费 | Next.js 友好，类型安全 |
| Strapi | Headless CMS | ✅ 开源免费 | 老牌，插件生态丰富 |
| Ghost | 博客平台 | ✅ 开源免费 | 适合内容站，自带后台与会员 |

> 这些都需要一台服务器（中国香港 / 海外，免备案）来运行容器。**「免费」指软件授权免费，运行所需的主机仍需自行准备**（云厂商低价轻量实例或闲置机，非长期免费）。

### 10.3 结论

- 「静态部署 + 后台实时生效」本身不成立：要么接受「改完重新构建」（Decap / Keystatic，免服务器），要么「上运行时」（Docker CMS 或 Cloudflare Workers + KV）。
- 「docker 服务器内的产品」有现成免费开源方案（Directus / Payload / Strapi / Ghost），但需要一台香港 / 海外容器主机来跑。

## 11. 长期免费主机与 Decap / Keystatic 详解

### 11.1 长期免费主机清单（免备案）

> 「长期免费」指可长期运行、无需付费。多数云厂商只有试用期 / 额度，真正长期免费的主机极少。

| 主机 / 服务 | 长期免费额度 | 可跑 Docker | 境外 / 香港区域 | 国内访问 | 适合 |
| --- | --- | --- | --- | --- | --- |
| **Oracle Cloud Always Free** | 2 台 ARM 实例（4vCPU/24G）永久免费 | 是 | 东京 / 首尔 / 孟买（无香港） | 尚可 | 首选免费容器主机 |
| **Cloudflare**（Workers/Pages/KV/R2） | 永久免费额度 | 否（Serverless） | 全球边缘 | 一般 | 方案 A |
| **Cloudflare R2** | 10GB 存储永久免费 | 否（存储） | 全球 | — | 存远程 JSON |
| **Supabase / Neon** | 免费 Postgres（长期） | 否（DBaaS） | 海外 | — | 配前端 |
| **Vercel / Netlify** | 免费层（非永久） | 否（PaaS） | 海外 | 偏慢 | 静态 / SSR |
| **GitHub Pages** | 永久免费 | 否（纯静态） | GitHub | 偏慢 | 纯静态 |

> 结论：想「免费 + 能跑 Docker 容器」（如 Directus / Strapi），**Oracle Cloud Always Free（亚洲区）** 是唯一的长期免费主机；区域选日本 / 首尔 / 孟买，国内访问尚可且免备案。Cloudflare 系则是「免服务器」路线的最佳免费底座。

### 11.2 Decap CMS（原 Netlify CMS）

- Git-backed：内容存 Git 仓库（JSON / Markdown），通过 GitHub / GitLab OAuth 登录，提供 Web 编辑器。
- 纯前端 + OAuth 代理，可托管在任意静态服务（Cloudflare Pages / GitHub Pages）。
- 流程：后台改 → commit 回 Git → 触发 CI 重新构建（分钟级生效）。
- 配置：`admin/config.yml` 定义集合与字段；无需后端、无需数据库。
- 适合非技术运营改文案；缺点：改动需重新构建、需 GitHub 账号。

### 11.3 Keystatic

- 新一代 Git-backed CMS，TypeScript-first、类型安全。
- `keystatic.config.ts` 声明 schema（JSON / YAML / Markdown），与 Next.js 集成好（`@keystatic/core`）。
- 同样写回 Git、构建时读取；提供本地 / 云编辑器。
- 相比 Decap：更偏开发者体验与类型安全、对 Next.js 更友好；Decap 更成熟、社区更大。

## 12. 自建轻量后端（Docker）：文件 or SQLite

> 不依赖现成 CMS、自己写后端时，「轻量」有两种落地方式；两者都适合单容器 Docker，且 Next.js 可前后端一体，无需独立后端。

### 12.1 「一个文件 + 内存」方案

- 配置存为单个 `config.json`（或 YAML），随镜像或 Docker volume 持久化。
- 服务启动时读入内存；后台 API 写入文件后，选择「重启容器」或「热重载（重新读取文件）」生效。
- 优点：零依赖、无数据库进程、读取极快、实现最简。
- 缺点：多副本不一致（单容器无碍）；并发写需加锁；结构校验弱。

### 12.2 SQLite 方案

- 单文件数据库（`data.db`），用 better-sqlite3 / Prisma 访问。
- 后台 API 直接读写，无需重启，天然支持事务与查询。
- 优点：比纯文件更严谨（约束/查询），仍是单文件、零运维。
- 缺点：需引入一个库；Docker 需 volume 挂载持久化。

### 12.3 架构与部署

- **前后端一体**：直接用 Next.js 的 Route Handlers / Server Actions 读写文件系统或 SQLite，单容器即可，省去独立后端。
- 架构：Docker（Next.js SSR）+ volume 挂载 `./data` → 服务读配置（内存或 DB）→ `/admin`（Token 鉴权）写配置 → 生效。
- 部署：镜像跑在 Oracle Always Free（亚洲）/ 香港 / 海外主机，免备案；域名解析到容器 IP。

> 推荐：单容器、低频改配置，「文件 + 内存」或 SQLite 都行；想要严谨选 SQLite，想要极致简单选「文件 + 重启/reload」。

### 12.4 单用户实时文件方案（写穿透，推荐）

只有一个人使用时，文件方式最合适，且能**不重启实时生效**：

- 配置存 `config.json`，Docker volume 持久化。
- 内存保留一份缓存 `cachedConfig`。
- 读取：`getConfig()` 直接返回内存缓存（快，无磁盘 IO）。
- 保存：`saveConfig()` **同时**写文件 + 更新 `cachedConfig` = 新值（写穿透）。
- 效果：后台保存后内存立即更新、页面立即生效，无需重启、无需每请求读盘；容器重启从文件自动恢复。

> 关键：「启动加载到内存」不等于「实时」——若只在启动时读盘，改文件不会更新内存。要让它实时，必须在「保存时同步刷新内存」，而不是只依赖启动快照。

### 12.5 本地开发与配置来源

- **配置文件位置**：项目内放一份 `data/config.json`（Docker 中由 volume 持久化）。本地 `pnpm dev` 直接读项目目录下的该文件，无需 Docker。
- **首次启动兜底**：`getConfig()` 若发现文件不存在 / 为空，使用内置默认值（即把现有 `profile.ts` / `homepage.ts` 内容作为种子）惰性写入文件，避免配置丢失。
- **与现有硬编码的关系**：把现有 `profile.ts` / `homepage.ts` 的常量改为「默认种子」，运行时统一从 `config.json` 读取，不再写死。
- **重要前提**：要「运行时读文件」必须放弃纯静态导出，改用 Node SSR 运行时（Next.js 标准 `next start` / Docker 部署），这正是「上运行时」路线的代价。

## 15. 纯静态前端构建（build:static，✅ 已实现）

> 在「Node SSR + Docker」主链路之外，额外提供纯静态导出能力，满足「不备案 + 国内流畅 + 零后端托管」的需求。

### 15.1 两套构建对比

| 命令 | 产物 | 后台实时编辑 | 部署形态 | 适用 |
| --- | --- | --- | --- | --- |
| `pnpm build` | `.next/standalone`（Node SSR） | ✅ 支持（需要 `/api/admin/config` 运行时） | Docker / Node 容器 | 主链路：后台可改、实时生效 |
| `pnpm build:static` | `out/`（纯静态 HTML） | ❌ 不支持（无服务端） | 任意静态托管 | 零后端、纯前端部署 |

### 15.2 命令与产物

```bash
pnpm build            # 默认：SSR + standalone，支持后台实时编辑（推荐用于自有服务器/Docker）
pnpm build:static    # 纯静态导出，产出 out/（配置在构建期烘焙进 HTML）
pnpm serve:static    # 本地预览静态产物：npx serve out
```

### 15.3 实现要点（为什么需要辅助脚本）

- `next.config.ts` 用 `BUILD_STATIC` 环境变量切换 `output`：`export`（静态）/`standalone`（SSR），并切换 `images.unoptimized`。
- API 路由 `/api/admin/config` 是 SSR 后台专用，静态导出无法运行服务端逻辑。
- Next 在 `output: "export"` 下要求路由显式声明 `export const dynamic = "force-static"`，但该声明会让 SSR 下 POST 鉴权读不到请求头；而 SSR 主链路需要 `force-dynamic`（实时鉴权）。
- 二者冲突，因此 `build:static` 调用 `scripts/build-static.mjs`：构建前把路由声明临时改为 `force-static` → 跑 `next build` → 结束后还原为 `force-dynamic`，保证 SSR 始终正确。
- 静态产物中 `/admin` 页面与 `/api/admin/config` 虽被导出，但后台写入在无服务端时不可用；改配置需重新 `build:static` 后重新上传 `out/`。

### 15.4 纯静态部署步骤

1. `pnpm build:static` → 得到 `out/`。
2. 将 `out/` 整个目录上传到任意静态托管：
   - **Cloudflare Pages**（静态上传 / 直接连 Git）：国内中等速度；
   - **GitHub Pages** / **Netlify** / **Vercel Static**；
   - **腾讯云 COS / 阿里云 OSS（中国香港地域）+ CDN**：国内最快、免备案。
3. 域名解析到对应节点（不指向大陆服务器，免 ICP 备案）。
4. 修改文案/数据时，改 `data/config.json` 或后台（SSR 环境）后重新 `build:static` 并重新上传 `out/`。

## 14. 最终落地实现：Node SSR + Docker（文件写穿透，✅ 已实现）

> 分支方向（用户确认）：「后续这个分支改为 Node SSR 和实际 Docker 部署的方式运行」。已按此落地。

### 14.1 架构

```
运营/本人 ──登录(Bearer Token)──> /admin 页面（client）──POST /api/admin/config──┐
                                                                                   ▼
                                   Next.js 服务端 Route Handler（server.js / Node SSR）
                                          │ saveSiteConfig()：写穿透
                                          ├─ 1) 更新内存缓存 cache（即时生效）
                                          └─ 2) 写入 ./data/config.json（持久化）
                                          ▼
访客 / 页面 ──> SSR 渲染 ──getSiteConfig()──> 直接读内存缓存（无磁盘 IO）──> 即时生效
```

### 14.2 文件映射（已实现）

| 文件 | 职责 |
| --- | --- |
| `data/config.json` | 唯一数据源（整站配置），Docker volume 持久化 |
| `src/lib/config.ts` | `getSiteConfig()` 读缓存/文件；`saveSiteConfig()` 写穿透；内置 `DEFAULT_CONFIG` 兜底 |
| `src/lib/site-config-context.tsx` | `"use client"` 的 `SiteConfigProvider` + `useSiteConfig()`，供客户端组件消费 |
| `src/app/api/admin/config/route.ts` | `GET` 返回配置；`POST` 携带 `Authorization: Bearer ${ADMIN_TOKEN}` 校验后保存 |
| `src/app/admin/page.tsx` | 后台编辑页（标量字段 + JSON 编辑器）；Token 存 localStorage |
| `src/app/layout.tsx` | 服务端 `getSiteConfig()` 驱动 metadata + JSON-LD，并包裹 `SiteConfigProvider` |
| 各 section / home / ui 组件 | 标量/数组配置改用 `getSiteConfig()`（服务端）或 `useSiteConfig()`（客户端） |
| `next.config.ts` | `output: "standalone"`（放弃静态导出，走 Node SSR） |
| `Dockerfile` / `docker-compose.yml` | 多阶段 `node:22-alpine`，挂载 `./data:/app/data`，`CMD node server.js` |

### 14.3 运行命令

```bash
# 本地开发：直接读项目目录 data/config.json（无需 Docker）
pnpm dev

# 生产构建（注意：本机 shell 若设了 NODE_OPTIONS=--use-system-ca，需先清空）
NODE_OPTIONS= pnpm build
# → 生成 .next/standalone/server.js（含 .next/static、public、data）

# 本地以 standalone 方式运行验证
NODE_OPTIONS= PORT=3000 node .next/standalone/server.js

# Docker（首次改 ADMIN_TOKEN 为强随机值）
docker compose up -d --build
# 访问 http://<host>:12002/   后台 http://<host>:12002/admin
```

### 14.4 关键约定

- **读取**：服务端组件用 `getSiteConfig()`；客户端组件用 `useSiteConfig()`（必须在 `SiteConfigProvider` 内）。
- **实时生效**：`saveSiteConfig()` 同时写内存 + 落盘，无需重启；单容器单进程缓存一致。
- **兜底**：`data/config.json` 缺失/损坏时回落 `DEFAULT_CONFIG` 并惰性写回。
- **安全**：后台写入必须经 `ADMIN_TOKEN`（环境变量，Docker 中默认 `change-me`，务必修改）；未携带/错误 Token 返回 401。
- **持久化**：`docker-compose` 把宿主 `./data` 挂载到容器 `/app/data`，容器重启配置不丢。
